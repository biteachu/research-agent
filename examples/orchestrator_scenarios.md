# 팀장 합성 검증 시나리오

실제 논문·학생 자료 없이 지침의 의사결정과 역할 경계를 확인한다.
아래 예상 행동은 시험 기준이며 실제 검색·다운로드·파싱 성공 기록이 아니다.

| ID | 입력 조건 | 예상 처리 |
|---|---|---|
| S1 | “AI 생명과학 설명 오류를 연구하고 싶어”만 입력 | 팀장이 범위를 확인하고 작성 역할의 진단·핵심 질문부터 진행. 검색·파싱 자동 추가 없음 |
| S2 | “이 PDF만 파싱해줘” | 파서 직접 진입. 작성·문헌검색 불필요. 직접 PDF 동일성 범위 구분 |
| S3 | 계획서까지만 요청 | writing만 범위에 기록하고 작성 결과·수정 제안에서 종료 |
| S4 | 게이트 revision_required | 검색 blocked. 차단 위치·수정 요청 보고. 원계획서 자동 수정 없음 |
| S5 | 검색 partial, 선정 2편 중 검증 PDF 1편 | 적격 1편만 파서에 전달. 선정 2·확보 1·미확보 1 구분 |
| S6 | 파서 completed, 품질 needs_review | 파싱 실행 완료·검토 필요 1건, 전체 partial. passed로 승격하지 않음 |
| S7 | 검색 대상 두 가지가 충돌, 사용자 선택 없음 | 팀장이 한 질문으로 선택 요청. 의존 검색 blocked, 독립 확인만 수행 |
| S8 | 중단 뒤 입력 SHA256 변경 | 이전 기록 보존, 후속 작업 blocked, 새 입력 재인계 필요. 기존 완료를 재표시하지 않음 |
| S9 | 하위 에이전트 도구 미지원 | 전용 지침으로 순차 역할 전환, execution_mode=role_switch와 agent_id=null |
| S10 | 재개 시 입력·출력 해시 모두 일치 | 유효 완료 작업 재실행 없음. 대기한 다음 단계만 진행 |
| S11 | 기존 manifest 1.0 또는 직접 PDF 파싱 요청 | 요청 범위의 파싱만 허용. 게이트 부재/직접 입력을 새 검색 승인으로 해석하지 않음 |
| S12 | 작성 재작성 2회 후 1점 항목이 남고 게이트는 ready, 작성→검색 범위 합의는 있음 | 작성 검토 pending_user, writing/search 작업 blocked. 미달·위치·횟수를 부록과 팀장 보고에 기록. 유효 잠정안이 있으므로 전체 partial. 기존 범위 합의로 새 수용 승인을 대신하지 않음 |
| S13 | S12 뒤 사용자가 미달을 남긴 잠정안 수용과 후속 검색 진행을 승인 | 작성 검토 accepted_provisional, writing partial. 실제 승인 기록·계획서 해시·게이트를 재확인한 뒤 검색 진행. 1점을 2점으로 바꾸지 않으며 미달이 남아 전체 partial |
| S14 | 잠정안 수용만 승인했고 후속 진행은 미승인, 또는 게이트가 revision_required | 수용만으로 검색하지 않음. 필요한 후속 진행 결정을 확인하고, 게이트가 revision_required이면 승인 여부와 무관하게 검색 blocked |
| S15 | 알려진 검토 대기·상한 중지가 없는 기존 계획서에 검색만 직접 요청, 작성 루브릭 기록 없음 | 새 작성 루브릭·작성 승인 요구 없음. 게이트와 기존 수정 이력은 확인하고 검색 허용 판정일 때 진행 |
| S16 | 게이트 count=1/total=1에서 승인된 다음 수정 회차를 작성 측이 검사하고 검색 측이 같은 회차를 독립 검사 | 작성 측 첫 재검사에서 count=2/total=2. 검색 측 검사는 같은 last_revision과 연결하여 2/2 유지. 검색 역할이 최초 검사자라면 그 역할이 한 번만 집계 |
| S17 | 동일 계획서·수정 회차에 수정 없이 판정 대조 또는 게이트 기록만 갱신 | count/total/last_revision 유지. 게이트 이력 보존. 판정 대조만으로 새 수정 회차를 만들지 않음 |
| S18 | 세 번째 수정 후 작성 측 ready이나 검색 측은 미해결 block을 발견하여 revision_required | 같은 회차 count=3 유지, stopped=true. 팀장이 남은 block·위치·결정을 보고하고 수정 반복·검색 인계 중지. 네 번째 자동 수정 없음 |
| S19 | 게이트 count=3/total=3/stopped=true에서 대화·실행ID·파일명만 바꿔 재개 | 기존 주기·횟수·중지 상태 복원. 새 실행으로 초기화하거나 직접 검색 요청으로 우회하지 않음 |
| S20 | S19에서 사용자가 남은 문제의 결정과 게이트 수정 재개를 명시적으로 승인 | 승인·과거 이력 보존, cycle=2/count=0/total=3/stopped=false. 수정 후 첫 검사에서 1/4. 게이트가 통과하기 전 검색 불가. 작성 재작성 상한은 별도 승인 없이 초기화하지 않음 |
| S21 | 기존 계획서를 검토만 요청했고 적용 항목에 1점이 있음 | 원계획서 수정 없음, 재작성 횟수 유지. 점수·위치·수정안 보고, findings_reported. 검토 작업은 completed로 종료할 수 있으나 계획서 통과로 표시하지 않음 |
| S22 | 문장 수정 요청에서 적용 항목은 모두 2점이고 연구 설계 등 항목 전체가 범위 밖 | 범위 밖 항목을 이유와 함께 N/A로 기록, 적용 항목만으로 passed. 전체 계획서 재작성·추가 설계 질문 없음 |
| S23 | 적용되는 윤리 항목을 점검하지 않았거나 근거 부족 때문에 해당 항목을 건너뜀 | N/A·2점 부여 금지. 미평가이면 점검 전 통과 불가, 근거 부족이면 확인 상태와 조치의 적절성을 실제 채점. 자료 부재만으로 무조건 0점 처리하지 않음 |
| S24 | 게이트 관리용 문자열이 없고 이력만으로 과거 수정 횟수를 확정할 수 없음 | 0으로 추정하지 않고 자동 수정 반복·후속 인계를 대기. 팀장 또는 직접 역할이 확인 요청. 신규 과제임이 확인된 경우에만 최초 주기 초기화 |
| S25 | 한 번의 승인된 수정이 작성 재작성과 게이트 수정에 모두 해당, 기존 작성 1회·게이트 2회 | 작성 재검토 후 작성 2회, 첫 게이트 재검사 후 게이트 3회. 검색 측 재검사에서도 게이트 3회 유지. 작성 미달 또는 게이트 revision_required가 남으면 해당 상한으로 중지 |
| S26 | 재작성 0회지만 사용자 결정 없이는 요청 범위 안에서 수정할 수 없음 | 상한을 채우려 반복하지 않고 즉시 pending_user. 승인되지 않은 수정을 하지 않으며 횟수 유지 |
| S27 | pending_user인 작성 과제를 검토 전용이나 직접 검색 요청으로 전환하되 미달 수용·후속 진행 승인은 없음 | 모드 전환으로 기존 대기를 해제하지 않음. 검토 결과 보고는 가능하지만 후속 검색은 대기 |
| S28 | 일부 세부 조건만 비적용이고 나머지 적용 조건에 결함이 있음 | 항목 전체를 N/A로 숨기지 않음. 비적용 이유를 남기고 적용 조건의 결함에 따라 0~1점 판정 |

## 상태 계약 합성 예시

필수 최상위 키: schema_version, run_id, created_at, updated_at, research_root,
scope, run_status, tasks, decisions, next_actions.
scope.agreed_stages는 writing/search/parsing 중 합의된 단계만 담는다.
작업별 status와 upstream_result의 원 판정은 분리한다.
입출력 해시는 실제 파일에서 계산하며 예시용 가짜 서지나 PDF 검증 성공을 만들지 않는다.
state.json과 team_report.md는 실행 자료이므로 이 공개 예시 파일과 달리 Git에서 제외한다.

작성 검토는 upstream_result.review_records에 kind=writing_review로 연결하고
pending_user 같은 검토 상태는 team_report.md에 보존한다. task.status의 blocked/partial/completed와
검토 상태·점수를 서로 대체하지 않는다. 검토 기록이 응답에만 있으면 path/sha256은 null이다.

게이트 횟수 표기 예시는 다음과 같다. 이는 합성 상태이며 실제 실행·승인 기록이 아니다.

```text
[gate_retry] cycle=1; count=2; total=2; last_revision=cycle1-revision2; stopped=false; resume_ref=none
```

동일 수정 회차의 검색 측 재검사에서는 이 횟수를 유지한다. 중지·새 주기 시작 시에는
기존 게이트 이력을 보존하고 실제 승인 기록 위치를 resume_ref에 연결한다.

## 반복 상한·루브릭 변경의 정적 검증 기록

검증 방식은 지침을 입력 조건에 적용한 수동 모의 판정이다. 실제 에이전트 실행,
검색·다운로드·파싱 시험이나 자동화된 런타임 차단 시험을 수행한 것으로 해석하지 않는다.

| 대조 사례 | 규칙 적용 결과 | 판정 |
|---|---|---|
| S12~S15, S27 | 게이트 판정과 작성 검토 대기를 별도로 적용하면 미승인 인계를 막으면서 검색 전용 요청에 새 루브릭을 강제하지 않는다. | 문서상 일치 |
| S16~S20, S24~S25 | 수정 회차 단위로 집계하고 주기와 전체 누적 횟수를 보존하면 이중 집계·모드 전환 초기화를 막고 두 상한을 독립적으로 적용할 수 있다. | 문서상 일치 |
| S21, S26 | 검토 전용은 원본 수정 없이 보고로 종료하고, 결정이 필요한 작성은 상한 전에 대기한다. | 문서상 일치 |
| S22~S23, S28 | 전체 비적용·부분 비적용·미평가를 구분하면 정당한 N/A만 제외하고 적용 항목의 미달을 숨기지 않는다. | 문서상 일치 |

기존 S1~S11도 역할 경계·게이트 차단·부분 완료·원본/해시 보존 규칙과 대조했다.
새 규칙은 작성 검토·인계 반복에 적용되며 PDF 파서의 실행 상태와 품질 판정을 변경하지 않는다.
